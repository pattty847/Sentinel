# S5 plan: HeatmapSourceController on the B1 hybrid (owner-approved 2026-09-30)

Implements slice S5 of `2026-09-gpu-heatmap-integration-plan.md` on the B1 hybrid design
(`2026-09-b1-whole-chunk-benchmark.md`), under the product contract in
`2026-09-heatmap-interaction-spec.md`. Drafted by a planning agent, reviewed by the
orchestrator, approved by the owner with the decisions in section 8.

## 1. Goal and scope

S5 turns the B1 hybrid prototype into production components:
- a process-wide chunk cache fed by the S3 wire;
- a per-chart controller that plans spans, builds tile-span `GpuSource`s off-thread and publishes them;
- a production `HeatmapTileNode` that owns every piece of GPU content it draws.

It is proven in `sentinel-lab` and in fake-transport tests.

S5 does **not** touch the main chart; that is S6. The legacy path stays untouched:
- the `DataProcessor` band path
- `HeatmapColumnWindow`
- `RecordingBandPolicy`
- UGR `ensureHeatmapRootNode`
- `MainWindowGpu`

Also out of scope:
- labels and walls (S7)
- legacy deletion (S8)
- the disk cache (after S6)
- the live edge (slice S5L, section 8)

No AGENTS.md hot file is touched.

## 2. Components, threads, data flow

**Core (`libs/core/heatmap`, QtCore only)**

- **`ChunkStore`, reshaped.** Today the loader is blocking and synchronous (`ChunkStore.hpp` Loader/`get()`), and insert takes `SparseColumns` by value, which forces a copy out of the client's `shared_ptr<const ChunkFrame>`.
  - Add `put(key, shared_ptr<const SparseColumns>` aliasing the frame, `ChunkState, contentHash)`.
  - Add a non-blocking `peek`.
  - Add a `contentHash` field on `StoredChunk`.
  - Keep tickets, generations and the revision listener.
  - Delete the blocking `Loader`/`get()` path in **S5c**, when the lab moves to a transport. S5a retains `Loader`/`get()`/`reload()`/`revise()` unchanged in meaning because the lab still uses them (owner's S5a hand-off clarification, 2026-09-30).
- **`ChunkTransport`** (new interface).
  - Call: `request(symbol, source, levelMs, starts, haveHash) -> req`.
  - Signals: received, failed, availability, connected, disconnected.
  - Implementations: an adapter over `SentinelStreamClient` (in `core/protocol`); `FakeChunkTransport` for tests; `LocalChunkTransport` for the lab, which reads HMC2 through `recording::buildChunk` as `LabChunks.cpp` does today.
- **`ChunkFetcher`** (new, one per process).
  - Dedups keys across all charts, batches up to 64 starts per request (`ChunkWire.hpp`), and caps in-flight work at 4 chunks / 16 MiB.
  - Backs off on `busy` and ignores `superseded`.
  - Maps request ids back to keys, so a keyless local `malformed` still fails the right keys.
  - Owns the per-source availability model and broadcasts `chunkStored` / `chunkRevised`.
- **`HeatmapSpanPlanner`** (pure functions). Extends `HeatmapTiles` (`chunksFor`, `tilesCovering`, `commonUnitsIn`) to several sources: which chunks each span needs, prefetch order, and the resolution summary.

**GUI (`libs/gui/render/heatmap`)**

- **`HeatmapSourceController`** (per chart, QObject).
  - Holds tf, tick request and view.
  - Plans spans with a rank: visible > fallback > prefetch > recent-tf.
  - Builds span `GpuSource`s on a shared bounded pool (2 threads).
  - Publishes an immutable, tick-free `shared_ptr<const SpanSet>`.
- **Process-wide span-source LRU**, keyed by (sources, tf, span, generations). Two charts showing the same span share one CPU build.
- **`HeatmapTileNode`** (render thread only).
  - Builds `(span, tick)` bins from the `SpanSet` itself (no lab `tickTileId` trick).
  - Owns wanted/held/fading retention.
  - Enforces the per-chart GPU cap and reports stats.

**Threads**

- The asio thread receives. The client's 1-thread decode pool decodes. Signals are queued.
- One process-wide "heatmap-data" QThread hosts the `ChunkFetcher` and all controllers.
- The build pool composes and builds sources. A per-chart serial number drops stale results.
- The GUI thread, in `updatePaintNode` (GUI blocked):
  1. takes the latest `SpanSet`;
  2. computes Auto tick with hysteresis from the snapshot's tick summary;
  3. hands a `Frame` to the node, so a tick change needs no thread hop;
  4. posts the tick to the controller, which uses it for near residency.
- The render thread owns every QRhi object.

**Flow**

1. The wire delivers a frame, and the client decodes it.
2. `ChunkFetcher::put` stores it in `ChunkStore` without a copy.
3. The controller plans spans and gets each span's `GpuSource` from the shared LRU.
4. It publishes a `SpanSet` snapshot.
5. The node uploads the resident sources, bins the rows around the view at the tick, and draws.

Pan and zoom only change the mapping.

## 3. Source selection, veil, tick

Mixing near and deep inside one `SparseColumn` is wrong. `binColumn` weights groups by `observedMs / column.observedMs`, which is the grid-change-over-time rule, not the rule for overlapping sources. A group with incomplete coverage also invalidates the cell.

Rule (owner decision 1):
- Each span keeps one source per source id.
- The node first bins the source with the coarsest tick that builds T (today: deep).
- A fill pass with the finer source (near) then writes only the cells the first pass left as veil (one uniform flag in the kernel).

What this gives:
- At $5/$10 and coarser, deep draws everything, and near need not be resident.
- At $1 to $2.5, near fills its +-5% band. Beyond the band is veil plus the resolution indicator; nothing is fabricated.

The controller attaches a `ResolutionSummary` to the `SpanSet`: per-column native ticks per source, and the near-band extents.
- **Auto** picks presets that every column can build **within the rows in view**.
- **Manual** offers every preset some loaded data can build (spec rule 4, option B).
- The indicator names the veiled columns and price ranges.

Near stays resident for visible and prefetch spans whenever the view overlaps the near band. It costs 23-47 MB (B1), and it makes a refinement to $1 appear in the next frame.

`hmc2.near` / `hmc2.deep` appear only as data in the source table (`ChunkCodec.hpp` `kChunkSources`). No S5 code branches on them.

## 4. Memory and budgets

- **Process RAM** (owner decision 4). Two configurable tiers:
  - decoded chunks: 512 MiB;
  - span sources: 256 MiB. These are evictable; they are rebuilt from chunks after a lost QRhi. The lab keeps them alive after upload; S5 does not.
  - A 1 GiB ceiling applies to CPU-side memory only.
- **GPU per chart.** Default cap 320 MiB (B1: 2x deep 1m peaks at 275 MB), configurable.
  - On Apple silicon, GPU memory is shared RAM; the per-chart cap is what bounds it.
  - The node enforces the cap on the render thread.
  - Eviction order: recent-tf, then far prefetch, then near prefetch.
  - Visible, fallback, held and fading content is never evicted.
- **Switch back to a recent tf in under 50 ms.** After a tf switch, the previous tf's visible spans stay resident as the recent-tf tier. A CPU rebuild cannot meet 50 ms: deep 1m 1x is 91 MB at 8 MiB per frame, about 11 frames.
- **(a) Retirement on the render thread** (B1 carry-over).
  - Today the node frees any tile missing from `Frame::tiles`, even while it is held or fading.
  - The lab evicts on the GUI thread from the previous frame's drawn ids, and it publishes only one previous tick. An A->B->C tick change under pressure therefore drops A's held tiles.
  - Fix: the node keeps `wanted | held | fading | fallback` and retires held and fading content itself when the transition ends. The controller never names tick tiles.
- **(b) Prefetch retry** (B1 carry-over).
  - Today suppressed prefetch comes back only when the plan or the budget changes.
  - Fix: the node bumps an atomic `capacityEpoch` whenever it frees bytes (a transition retires, or a revision shrinks a source).
  - The controller then re-admits prefetch strictly by rank, only when `free >= bytes + 10%`.
  - Eviction may only remove lower-rank content than what it admits. That strict order means the evict/rebuild ping-pong cannot come back.
- **Prefetch width.** At least 2 tiles, or one view width, per side. B1 measured 1 tile at p95 56-59 ms on small horizontal pans. This replaces the plan's "+-1 view" and the lab's 1 tile.

## 5. Reconnect and revisions

- **Disconnect.** Every in-flight request is lost: the epoch drops replies, and `connectToServer` clears the write queue, so a request sent while disconnected vanishes. The fetcher marks those keys pending and re-sends them after `connected()` and a fresh availability message.
- **Open chunks after reconnect.** They are re-requested with `have_hash`.
  - `NotModified` keeps the generation, so there is no rebuild.
  - A new body goes through `revise()`, and the listener broadcasts it (queued) to every controller.
- **Committed-through advance.** When an availability push advances a level's `committed_through_ms`, the fetcher re-requests the open chunks some chart wants.
- **Sealing.** A chunk that becomes sealed gets a new generation, once.
- **Stale spans.** They keep drawing the old version as the slot fallback until the rebuilt span is resident. This is how the owner's "old picture keeps drawing until the new one is ready, never blank" (active/spare) is met in the hybrid design.
- **Wire version mismatch:** refuse and clear. **Host change:** clear the store.

## 8. Owner decisions (2026-09-30)

1. **Source rule.** Deep wins wherever it can build the tick, and near fills only the veiled cells. Auto is judged on the rows in view, not on whole columns. Judged on whole columns, Auto could never reach $1 while deep data exists.
2. **Live edge.** A new slice, S5L, runs before S6.
3. **`ChunkDiskCache`.** Deferred until after S6. When it lands, every disk hit is validated with `have_hash`.
4. **Defaults.** 512 MiB decoded chunks, 256 MiB span sources, a 1 GiB CPU-side ceiling, and 320 MiB GPU per chart. All are configurable. Price-banded deep (not yet measured) is the lever if these are exceeded.
5. **B1 comparison modes.** Deleted in S5c, after the final bench against the B1 numbers: full/V/W-gpu/W-cpu, `TileRef::cells`, and the `HeatmapRenderNode` active/spare path. `buildCells` stays as the test oracle.

Unchanged from the spec: Auto (default) and Manual tick, with Manual remembered per symbol and timeframe, the veil and the resolution indicator, and a 150 ms crossfade. There is no auto-timeframe. S6 adds the Auto/Manual toggle and the preset selector to the main chart.

## S5b implementation notes and deviations (2026-09-30)

Codex gpt-6-astra started S5b and was stopped by a usage limit; a Claude
lieutenant finished it. Where the result differs from sections 2-4:

1. **One build per (span, source), not per span.** The span-source LRU key is
   (span, source id, the source's availability clipped to the span, price
   scale, chunk generations). A source builds as soon as its own chunks are
   local, so a coarse source can draw before the fine one arrives, and a
   revision of one source's chunk rebuilds only that source. The node still
   receives every source of a span, coarsest common tick first.
2. **Serial.** The per-chart serial changes on a symbol change, a tf change and
   a store clear, not on a pan: a pan keeps the builds already running for spans
   it still plans. A result is also dropped when its slot has since asked for a
   different key (a revision arrived mid-build).
3. **Fallback tier.** The controller has no tick tiles, so "fallback" is the
   previous tf's built visible spans while the new tf's visible spans build
   (never evicted); once the view is complete they become recent-tf. Retained
   spans want no chunks and are not rebuilt; a revision reaches them when they
   are visible again.
4. **Auto over the summary** (owner decision 1, made precise): a preset is
   eligible when every row in view that some source fully covers is covered, in
   whole tick bins, by a source whose common tick divides it. Rows no source
   covers (outside the book, coverage holes of every source) are ignored: they
   veil at any tick, and counting them would stop Auto whenever the view leaves
   the book. `veiledRanges` reports exactly the rows that block a preset.
5. **Capacity contract (node side, for S5c).** The node calls
   `HeatmapCapacity::report(freeBytes, uploaded, lost)` whenever its resident
   bytes change: after uploads as well as after releases. `freeBytes` is the
   per-chart cap minus resident bytes; `uploaded` names the span sources
   (`SpanSourceKey`) it uploaded since its last report; `lost` says it lost its
   GPU copies (QRhi loss). The controller's credit is the reported free bytes
   minus its outstanding reservations: every admitted source not yet reported
   uploaded, at its built size, else its size hint, else the estimate. A build
   smaller than its estimate therefore returns credit at once, an evicted or
   cancelled admission stops counting, and a static view makes progress without
   new reports (review fix 6). Before the first report the credit base is the GPU cap.
   **Image ownership:** once the node reports a source uploaded, the controller
   releases its CPU image. The snapshot keeps the metadata (`SpanSourceBuild`
   with `gpu == nullptr`, same key), and the node draws its resident copy. After
   `lost`, the controller rebuilds released images from the local chunks.
6. **Tick request.** `setTickRequest` is stored and logged only; near residency
   by tick is a node decision (S5c). Sources stay tick-free.
7. **No static cache instance.** The owner of the heatmap-data thread creates
   the one `SpanSourceCache` and passes it to each controller. A chunk that
   failed terminally is left out of its span's build (those buckets draw
   loading) instead of blocking the span forever.
8. **Location.** The controller stays in `libs/gui/render/heatmap` because it
   builds `gpu::GpuSource`; it uses QtCore only and its test links no GPU code.
9. **CPU tier (review fix 3).** `SpanSourceCache` pins claimed images (one claim
   per slot source, a key counted once however many charts hold it) plus the
   reservations of running builds. Unclaimed LRU images fill only what is left.
   When claimed bytes exceed the tier, the cache drops the lowest-rank slots of
   all controllers (prefetch and recent-tf, never visible or fallback), and
   prefetch admission needs CPU room at the size hint of past builds.
   `SpanSourceBuild::bytes` is the CPU allocation (vector capacities);
   `uploadBytes` is the GPU payload used for the GPU cap and credit.
   `Stats::liveBytes` counts every image alive anywhere; snapshots can hold an
   image one frame longer than its slot.
10. **Decoded chunks (review fix 1).** The store never evicts a key that some
    chart wants (`ChunkStore::setWanted`, maintained by the fetcher), even a
    single chunk larger than the whole budget; the byte cap evicts unwanted
    chunks only, and `Stats::wantedBytes` shows what wanted keys retain. A
    working set above the budget would otherwise evict bodies before their
    spans build and refetch them forever.
11. **Availability per level (review fix 5).** `tiles::Availability` carries
    `minuteOldestMs` and `hourOldestMs`. Hour chunks cover only the advertised
    hour interval; an hour chunk scans its whole day, and a coarser level's
    gaps supersede minutes, so the day holding the first rollup composes from
    minutes whenever minute history reaches it.
12. **Admission order (review fix 4).** Every surviving slot takes its new plan,
    rank and sources before usage is measured or anything is admitted.
13. **Stale results (review fixes 2 and 7).** A serial change forgets pending
    builds, so a return to a tf rejoins the build or takes it from the cache. A
    completion is accepted only when it matches both the pending request and
    the source's current desired key; otherwise the published version stays.

14. **Process-wide CPU ceiling (re-review P1, orchestrator policy).** Every
    controller commits what it pins to a ledger in `SpanSourceCache`: its wanted
    decoded chunks (measured size, else a size hint, else 4 MiB) plus its span
    images (claimed images, plus an estimate for each source that still needs a
    build). It keeps the ledger total at or under `HeatmapBudgets::cpuCeiling`
    (1 GiB default, `SpanSourceCache::setCpuCeiling`). Above it the chart gives up
    recent-tf, then prefetch (farthest first), then fallback, then the visible
    spans farthest from its view centre (visible ranks now carry their distance
    from the centre tile). Its nearest visible span always stays, alone even
    above the ceiling. Refused visible spans draw as loading, not veil; they are
    in `SpanSet::refused` / `refusedBytes`, in `Stats::refused` / `refusals`,
    and in a warning throttled to one per 5 s per chart (chart, symbol, tf,
    bytes, committed total, ceiling). Charts commit in turn, so the chart that
    arrives second gives up its far visible spans first. Shared chunks and
    images are counted by every chart that holds them, which over-counts and so
    stays safe. The ledger total also counts each build job no chart covers
    (its reservation plus its input chunk bytes, held until it finishes even
    after a refusal, pan, serial change or chart close). A chart covers the keys
    it has pending, so a job is counted once; its finish fires `capacityFreed()`.
    When a commitment raises the total above the ceiling (a chart down to its
    keeper), the cache emits a coalesced `overCeiling()` and every chart sheds by
    its own loss order while the total is over, never below its keeper. Shedding
    never raises the total, so this cannot oscillate. `reset()` and an empty view
    commit zero and clear the refusals.
15. **Chunk wants follow builds.** A source wants every chunk of its plan only
    while it needs a build (never built, changed plan, revised chunk, GPU
    loss). Once built, only its open (unsealed) chunks stay wanted, so their
    revisions arrive; sealed chunks become evictable at once, before the upload.
    I chose that over waiting for the upload because nothing reads a built
    source's chunks again unless it rebuilds, and every rebuild path wants them
    again: a GPU loss resets the released image, and a CPU drop re-admits it as
    new. `ChunkGeneration::sealed` records which chunks a build used were
    sealed. A `chunkRevised` for the chart's symbol schedules a reconcile even
    for a chunk no longer wanted.
16. **GPU loss and retained spans (re-review P2).** On loss, a released fallback
    image (it is drawn) is rebuilt from its chunks; a recent-tf span whose image
    was released is dropped instead of rebuilt.
17. **Plan changes invalidate at once (re-review P2).** A changed plan (bounds,
    scale, chunk set) or a revised chunk sets the source's expected key right
    away, even while a new input is still missing, so a build of the old plan
    that completes meanwhile is rejected. The build key carries `planHash`, a
    hash of the complete planned chunk-key list, so a plan that gains a
    dependency differs even before that chunk arrives. The published version stays as a
    stale fallback.
18. **Freed capacity wakes charts (re-review P2).** The cache emits
    `capacityFreed()` at most once per event-loop turn when claims, reservations
    or ledger commitments shrink. A controller that suppressed or refused work
    for CPU room reconciles on it; `schedule()` coalesces it to one reconcile per
    turn. `budgetsChanged()` reconciles every chart after a tier or ceiling
    change. The CPU gate also counts admitted sources that are not built or
    requested yet.
