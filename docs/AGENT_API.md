# Agent API (v1)

The GUI listens on `127.0.0.1` at `gui.api_port` (default `17100`). `api_port=0` disables it. This is a local observation API; reads do not fetch history. All times are UTC epoch milliseconds. It currently exposes these routes:

| Method | Route | Result |
|---|---|---|
| GET | `/api/v1/state` | Connection, advertised server configuration, active layers, receive times and chart render statistics. |
| GET | `/api/v1/viewport` | Active chart bounds, linked heatmap/candle timeframe, follow mode, auto price scale (`autoScale`), dimensions, zoom and viewport version. |
| GET | `/api/v1/candles?startMs=...&endMs=...&timeframeMs=...&limit=500` | Locally held candle bars and `nextStartMs` for pagination. `limit` maximum 2,000. |
| GET | `/api/v1/book?levels=20` | Best prices, spread, up to 200 levels per side, band and receive time. |
| GET | `/api/v1/trades?windowMs=60000&limit=100` | Receive-time tape, newest first, and summary of all retained matches. Window maximum 900,000 ms; limit maximum 1,000. |
| GET | `/api/v1/heatmap/state` | Renderer, tick and settings, shared service status, and (gpu renderer) the live layer: settled, drawn tf/tick, presets, live age, GPU bytes, controller stats. |
| POST | `/api/v1/heatmap/settings` | Partial chart settings; optional `persist:false`; returns an operation ID. |
| POST | `/api/v1/input` | Synthetic wheel, drag or click to the heatmap QQuickView; returns an operation ID. |
| GET | `/api/v1/heatmap/walls?from_ms=...&to_ms=...&tick=...&priceMin=...&priceMax=...&minQty=0&limit=20` | Recording walls ranked by peak resting size. GPU defaults to the viewport; legacy defaults to the loaded window. `limit` maximum 100. |
| GET | `/api/v1/screenshot?name=review&target=main` | Existing screenshot result; `target` is `main`, `heatmap`, `lab`, or (S6c widget grabs) `settings`, `settings:<Chart|Tick|Look|Budgets|Live|Debug|TPO>`, `telemetry`, `toolbar`, `chartmenu`. |
| POST | `/api/v1/symbol` | JSON `{"symbol":"ETH-USD"}`; subscribes through the chart's symbol path. |
| POST | `/api/v1/timeframe` | JSON with `heatmapTimeframeMs` and/or `candleTimeframeMs`; v1 links them and requires an advertised served timeframe. |
| POST | `/api/v1/viewport` | JSON with paired `startMs,endMs`, paired `priceMin,priceMax`, `followLive` and/or `autoScale` (the auto price scale, the "A" toggle); or `{"fit":"time"|"price"|"both"|"default"}` (the axis double-click actions). |
| POST | `/api/v1/layers` | Partial boolean map for `heatmap`, `candles`, `footprint`, `tpo`, `volumeProfile`; optional TPO look strings `tpoLayout` (`split`, `collapsed`) and `tpoTheme` (`rainbow`, `calm`, `sage`). State `layers` reports both. |
| GET | `/api/v1/operations/<id>?waitMs=5000` | Current operation state; waits at most five seconds for a rendered frame. |
| GET | `/screenshot?name=review&target=main` | Legacy screenshot route and response, retained for existing agents. |

State, viewport, candles, book, trades and walls accept optional `symbol=<active-symbol>`; a different symbol returns `409`. `servedTimeframesMs` comes only from the server's advertisement. An older server that omits it yields `null`, distinct from an advertised empty array. Other unavailable configuration fields and unseen receive timestamps also yield `null`. `selectionEpoch` is a decimal string and advances when the active symbol or timeframe changes, or connection status changes. `sessionId` changes on each GUI run. `viewportVersion` is a decimal string when the viewport is valid. An unknown viewport field is `null`.

State `data.render` contains `frameP50Ms`, `frameP95Ms`, `rateHz`, and `idle`. Durations cover CPU work on the chart render thread from scene synchronization through render command submission; they do not measure GPU completion. Percentiles use rendered frames from the preceding one second and are `null` if that window has no frames. `rateHz` counts renders in that same one-second window, including data-driven renders, so it is not an FPS capacity estimate. `idle` means no mouse, touch, wheel, or keyboard input reached the chart in the past second. The GUI refreshes these values four times a second.

Successful state and viewport responses have `{"ok":true,"meta":{"sessionId":"...","symbol":"BTC-USD","selectionEpoch":"1","observedAtMs":1790596800000,"source":"gui-cache","stale":false,"coverage":"unknown","truncated":false},"data":{...}}`. Errors have `{"ok":false,"error":{"code":"not_found","message":"Unknown route"}}`. Screenshot success retains `{"ok":true,"path":"./screenshots/review.png","target":"main"}`. The v1 route also accepts `afterOperation=<id>&waitMs=0..5000`; it captures only after that operation renders, returning `408 render_timeout` if no frame arrives, `409 operation_not_rendered` if superseded or failed, and `404 unknown_operation` for an unknown ID. A guarded screenshot includes decimal-string `frameId`, `viewportVersion` and `selectionEpoch`. Screenshots are limited to one request per second (`429`).

Requests must use HTTP/1.1 and a `Host` of `localhost` or `127.0.0.1`, with an optional port. A browser `Origin` is rejected. Headers are capped at 8 KiB and bodies at 16 KiB; POST controls require `Content-Type: application/json`. GET requests do not accept bodies. The server allows eight concurrent connections and closes stalled requests. Sockets and handlers currently run on the GUI thread; operation waits use short timer callbacks and do not block the event loop. PNG encoding/writing remains synchronous and can pause the GUI.

## Controls and render ordering

Every successful POST returns an `operationId` and `status:"applied"`, plus the changed state. GET `/operations/<id>` returns `applied`, `rendered`, `superseded`, or `failed`; it includes `viewportVersion`, and a rendered operation includes `frameId`. A later control of the same kind supersedes a pending one. `waitMs` expires with the current state (usually `applied`) and does not imply failure. Unknown IDs return 404. Operations are retained for the newest 256 IDs.

`/symbol` accepts uppercase `BASE-QUOTE` symbols with two to twenty ASCII alphanumeric characters on each side. `/timeframe` requires an advertised `servedTimeframesMs` entry; older servers without that advertisement cannot select a timeframe through this API. Either field sets both v1 timeframes, and unequal values return 422. `/viewport` requires each bound pair to be complete, finite, positive for price, and increasing. Explicit time bounds turn off follow mode; neither bound pair can be combined with `followLive:true`. Omitted price bounds preserve the current price range (gpu with the auto price scale on: fitted to the visible candles, below). Follow-only requests preserve the current price span and recenter it on the latest best bid/ask midpoint, falling back to the last trade until a two-sided book arrives. An explicit price range disables follow mode. Viewport changes use `setViewport()` so the version advances.

Auto price scale (gpu renderer; docs/research/2026-10-viewport-autoscale.md). `autoScale` (GET and POST) is the TradingView-style "A" toggle in the chart's axis corner, on by default. While on, the price range is the visible candles' high/low plus a 6% margin each side, refitted in the same viewport change as every time change (pan, wheel, time-axis zoom, follow-live step, timeframe switch, time bounds) and on candle updates or history pages in view (one change, none when the fit is unchanged); with no visible candle the price stays. While on, chart drags and keyboard pans move time only and the chart wheel zooms time only; during a drag the fit follows the window on screen (the drag commits only at release), so revealed candles fit as they appear. A price-axis drag or wheel, Shift+wheel, or explicit price bounds (even equal to the current ones) turn it off; off, the price range stays where it was left, also across timeframe switches, and drags pan price again. A request resolves its flags (`autoScale`, `followLive`, bounds) and final window first and commits them as one viewport change (e.g. `{"autoScale":true,"followLive":true}` is one change at the live edge, fitted). `autoScale:true` fits at once (as the price-axis double-click; with nothing to fit yet it is on and the next candles fit; with time bounds the bounds land fitted); it cannot come with price bounds (`422 invalid_auto_scale`) and returns `409 auto_scale_unavailable` with the legacy renderer. A symbol switch keeps the state: on, the new symbol's candles fit; off, the span is carried as a fraction of the price with the current price (book mid, last trade, decoded data, newest close) at the same screen height, applied at the new symbol's first usable price (a symbol left before it got one passes the earlier carry on; a user price action cancels it). Until the new symbol's price scale is known (its own recorded availability; also before the first snapshot exists) the price-span limits are unknown (no clamp from another symbol's or the fallback scale); once known the carry is applied again from the then current price. A live-only symbol (no recorded availability) never gets one: 2 s after its first usable price the carry is applied from the live price and consumed, and that symbol has no Manual max span (nor zoom-in floor) until a recorded scale arrives. Under a Manual tick whose 1 row/px limit cannot hold the candles, the tick is kept and the max span is centred on the current price (book mid, then last trade, then the newest close).

Time (gpu): a timeframe switch keeps the bar width (the span scales by the timeframe ratio, inside the 1 column/px limit) and, when the Now column (the live bucket) is in view or the view follows live, keeps the Now column's screen x; a historical view keeps its end. A symbol switch keeps the time window.

`fit` stands alone (with bounds, `followLive` or `autoScale` it returns `422 invalid_fit`) and needs the gpu renderer: `time` shows the data's available time range (recording availability, else the candle series) clamped to the 1 column/px max span, ending one follow-live padding past the live bucket when following live or when all of it fits, else keeping the view centre inside the data (with the auto price scale on, the price follows); `price` (the price-axis double-click) turns the auto price scale on and fits the visible candles, or with no visible candle keeps the span and centres the live price (book mid, last trade, decoded data); `both` does both, all or nothing (if either part cannot fit, nothing changes); `default` (the time-axis double-click) resets to the default view: auto price scale and follow mode on, the initial span (initial_column_px per bar) ending one follow-live padding past the live bucket, price fitted. Each is one viewport change; `time`, `price` and `both` keep follow mode. With the legacy renderer or nothing known yet (no live anchor for `default`) it returns `409 fit_unavailable` and changes nothing (the auto price scale and follow mode stay as they were).

The render acknowledgement is an ordering guarantee: the renderer copies the GUI control revision, selection epoch and viewport version into its frame context, and publishes fixed-size atomic frame data after rendering. It does not assert that history is complete or that live data did not advance. A hidden chart can leave an operation `applied`, so a guarded screenshot can time out. Existing layer setters may disable conflicting layers; the response reports the resulting full layer state.

## Heatmap plumbing (S6a) and the GPU renderer (S6b)

S6b: with the gpu renderer active (`activeRenderer:"gpu"`), `heatmap/state` replaces the S6a `null` fields with the chart layer's values: `settled`, `tickMode`, `tickUnits` (the drawn tick, integer price units), `tick`, `manualTickUnits`, `offeredPresets` (units), `drawnTimeframeMs`, `drawnTickUnits`, `indicatorText` (the veil indicator, empty when none), `residentBytes`, `gpuBytes`, `liveVersion`, `liveAgeMs` (data age of the newest drawn live version at its first draw), `liveAgeP50Ms`/`liveAgeP95Ms`/`livePublishP95Ms` and `liveSamples` (over the drawn live versions since start), `prepareMs`, `lastBinMs`, `gpuFrameMs`, slot counts and `controllerStats` (refreshed asynchronously: `null` on the first read). `POST /api/v1/heatmap/settings` now drives the chart: `renderer` flips it at runtime, tick mode/manual tick, palette, sensitivity, opacity, crossfade and budgets apply at once. `state.heatmapReceivedAtMs` is the receive time of the newest live version in gpu mode. `GET /api/v1/heatmap/walls` supports gpu mode through the S7a CPU cell query described below. Wheel, axis drags, `POST /api/v1/viewport` and `/input` obey the same zoom clamps in gpu mode (GridViewState max spans; wheel and axis zoom-in also stop at 4 columns and 4 rows of the Manual tick or the finest offered preset). Zoom scales the spans themselves (no relative zoom factor), so the wheel zooms out to the max span from any view, including one an axis drag widened. `POST /api/v1/timeframe` in gpu mode keeps the columns on screen (the span scales with the timeframe about the Now column when it is in view or following live, else about the view end, clamped), so the viewport version advances with the timeframe (S6d). The A/B script `scripts/dev/heatmap-ab.sh` drives two processes through this API; screenshots are limited to one per second per process, so pace guarded shots accordingly. A drag left without `dragMove`/`dragEnd` for 10 s is released at its last position.

S6c: `heatmap/state` adds `ui`: `toolbar` (`enabled` false with the legacy renderer, `mode`, `shownTickUnits` = the drawn tick in Auto or the locked preset in Manual, `presets` = the offered presets, `presetText`, `veiled` = the resolution indicator is non-empty), `telemetryVisible` (the dock is on screen: shown and, when tabified, the current tab), `telemetryPreferred` (the saved `showTelemetry`), `settingsDialogOpen`, `budgets` (the process tiers: `decodedChunkBytes`, `spanSourceBytes`, `cpuCeilingBytes`) and `savedRenderer` (what a restart uses). A `heatmap/settings` POST goes through the chart's settings model, the same object the settings dialog, the toolbar tick selector and the telemetry dock use, so they all show the change at once (`showTelemetry` shows or hides the dock). The widget screenshot targets `settings` (opens the Heatmap Settings dialog; `settings:<Tab>` selects a tab), `telemetry` (the dock; `telemetry_not_visible` unless shown) and `toolbar` grab the widget's own painting (`QWidget::grab`), never screen pixels, so other windows can never appear in them (FM-120).

S7b: gpu-mode `heatmap/state` adds `labels`: `posted`, `results`, `retries`, `failures` (label window requests and their outcomes), `drawing` (a result matched to the drawn picture is drawn now) and `liquidityLo`/`liquidityHi` (the label window's 5th percentile and maximum cell size: the range slider's ends). `ui.toolbar` adds `shown` (which toolbar controls the active layers show: `tickSelector`, `palette`, `liquidity`, `rangeSlider`, `thresholdSlider`, `candleStyle`, `tpoSession`, `tpoLayout`) and `liquidityRange` (`low`/`high` handles, `endLo`/`endHi` ends). The widget target `chartmenu` grabs the chart menu (gear) and `settings:Chart` the dialog's Chart tab. Labels are drawn only from the current cell-query result whose timeframe and tick are the drawn picture's and this frame's target, only on columns whose drawn content (span build generations, live version) is the one the result was computed from; none during a crossfade or a hold. `ui.toolbar.shown.labelsToggle` is false with the legacy renderer.

`GET /api/v1/heatmap/state` uses the standard `ok/meta/data` envelope and accepts only optional `symbol=<active-symbol>`. `data.renderer` is the effective process selection (`legacy` or `gpu`); `activeRenderer` is `legacy` throughout S6a, including when the selection is `gpu`. Drawing, tick policy and runtime application arrive in S6b. `tickMode` is `auto` or `manual`; `tickUnits` is the effective manual tick (integer price units, price times the source's `priceScale`) in manual mode and `null` in auto mode. `settings` contains the complete effective chart model, including any process-only overrides. The fields `offeredPresets`, `settled`, `drawnTimeframeMs`, `drawnTickUnits`, `indicatorText`, `residentBytes`, `gpuBytes`, `liveVersion`, `liveAgeMs`, and `controllerStats` are `null` until the S6b chart layer supplies them. `service` reports `connected`, `availabilityReady` for the active symbol, `committedCpuBytes`, and `chunkRequests` (stats refreshed at 4 Hz). No controller, historical fetch or live subscription is created by this read.

`POST /api/v1/heatmap/settings` accepts any nonempty subset of `renderer`, `tickMode`, `manualTick`, `minRowPx`, `hysteresis`, `crossfadeMs`, `showBandEdges`, `palettePreset`, `bidGradient`, `askGradient`, `sensitivityMin`, `sensitivityMax`, `opacity`, `gpuCapBytes`, `uploadBudgetBytes`, `prefetchTiles`, `liveMinIntervalMs`, `showTelemetry`, and (S7b) `showLabels`, `labelCurrency` (`usd`/`asset`), `labelMinPx`, `labelMaxPx`. Unknown keys, wrong types, invalid enums and malformed gradients return 422 without changing settings. Finite numeric settings clamp to the limits in [CONFIG.md](CONFIG.md#heatmap-chart-settings-s6); fractional values for integer fields are rejected. The response contains the normalized settings/state and `operationId`/`status`. In S6a this acknowledges application of the settings and the normal frame ordering; it does not activate GPU drawing or mute the legacy processor. Process CPU budgets are shared settings, outside this per-chart patch.

The optional boolean `persist` defaults to `true`. Use `{"renderer":"gpu","persist":false}` for an A/B or agent process: no QSettings or shared manual tick memory is written. At least one chart field is required (`persist` alone is invalid). Later persisted patches save only their supplied fields against the latest stored model, so an unrelated opacity change cannot persist a temporary renderer override. The response echoes `persist`. Only an explicit `manualTick` in a persisted manual-mode patch updates shared symbol/timeframe tick memory; entering manual mode alone leaves that memory intact. Named workspace snapshots contain persisted settings, excluding process-only overrides. `_last_session` neither saves nor restores heatmap settings; live `heatmap/<chartId>/...` values remain the startup source of truth after a crash. Explicitly restoring a named workspace replaces the effective chart settings and persists that snapshot.

`POST /api/v1/input` accepts:

```json
{"kind":"wheel","target":"chart","x":300,"y":200,"deltaY":120,"modifiers":["shift"]}
```

`kind` is `wheel`, `dragStart`, `dragMove`, `dragEnd`, `click`, or `doubleClick` (press, release, press, double-click, release, as Qt 6 delivers it; on `priceAxis` it turns the auto price scale on and fits, on `timeAxis` it resets to the default view). `target` is `chart`, `priceAxis`, or `timeAxis`. Required `x,y` are finite, nonnegative logical pixels **relative to the target region's top-left**, strictly inside that region (right/bottom edge excluded). The regions use the current renderer geometry: chart content, its right price gutter, or its bottom time gutter; the corner is excluded. Values above 1,000,000 are rejected at decode time. `deltaY` is required only for wheel, an integer in -12000..12000 excluding zero, in Qt angle-delta units (120 is one wheel notch). Omit it for mouse kinds. Optional `modifiers` is a distinct array drawn from `shift`, `control`, `alt`, `meta`. Unknown fields, missing coordinates, invalid kinds/targets/modifiers or out-of-region positions return 422 before sending an event.

Drags use the left mouse button. `dragStart` presses, `dragMove` moves with that button held, and `dragEnd` releases it. Move/end require an active drag on the same target; other inputs during a drag return `409 drag_active`. Unmatched move/end return `409 no_drag`. A click sends a press/release pair. Each wheel request sends exactly one `QWheelEvent`; the host sends events synchronously on the GUI thread through `QCoreApplication::sendEvent` to the heatmap dock's `QQuickView`. Successful requests return an operation ID with the same frame acknowledgement rules as `/viewport`; they do not promise data completeness. A missing view returns 503.

```sh
curl -s 'http://127.0.0.1:17100/api/v1/heatmap/state'
curl -s -H 'Content-Type: application/json' -d '{"renderer":"gpu","tickMode":"manual","manualTick":100,"persist":false}' http://127.0.0.1:17100/api/v1/heatmap/settings
curl -s -H 'Content-Type: application/json' -d '{"kind":"wheel","target":"chart","x":300,"y":200,"deltaY":120}' http://127.0.0.1:17100/api/v1/input
# Use the returned operation ID; chart evidence uses target=heatmap (FM-120).
curl -s 'http://127.0.0.1:17100/api/v1/screenshot?name=wheel&target=heatmap&afterOperation=o3&waitMs=5000'
```

## Local evidence reads

All three reads use the same `ok/meta/data` envelope as state and viewport, with UTC epoch milliseconds. `startMs,endMs` is half-open: a candle whose start equals `endMs` is excluded. Candles are copied from the GUI's local series only; a timeframe without a local series returns `422 timeframe_unavailable` and no history request is sent. `nextStartMs` is the actual start of the next retained bar, or `null`. Gaps in locally held history mean candle coverage remains `partial` when bars exist.

Book levels are price/quantity pairs, bids descending and asks ascending. Missing best prices and spread are `null`. `bandLimited` is true because the replica only covers its configured band; `band` is null until it is initialized. A preallocated occupancy bitmap finds populated levels; the read examines at most 16,384 bitmap words (covering 1,048,576 price slots) per side under the book lock. If it cannot reach all requested levels, `scanLimited` and `meta.truncated` are true; a null best price in that case does not prove the full band side is empty. `receivedAtMs` is the GUI's most recent book receive time.

Trades are held in a preallocated GUI ring, capped at 10,000 rows and 15 minutes. Each row has `receivedAtMs`, `eventTimeMs:null`, `id`, `side`, `price` and `qty`; `timeBasis` is `received` because wire event time is currently discarded. The summary counts and sums every retained trade in the requested window, even when `limit` returns fewer rows. `meta.truncated` marks that row limit; `retentionLimited` marks a capacity eviction inside the requested window. A symbol, timeframe or reconnect epoch change excludes prior epoch rows.

## Heatmap walls

`GET /api/v1/heatmap/walls` scans on request from client-held recording data; it never fetches history. In gpu mode, omitted bounds use the chart's current visible time span and its visible price span extended by one view height above and below (clamped at zero). Explicit `from_ms`/`to_ms` select a half-open period of bucket starts and must be supplied together. The existing `startMs`/`endMs` spellings remain accepted; supplying both spellings of one bound is an error. Optional `tick` overrides the drawn tick in gpu mode and must be positive, finite and representable in integer source price units. `priceMin`/`priceMax` include overlapping price cells. `minQty` defaults to 0 and must be finite and nonnegative; `limit` defaults to 20, maximum 100. A tick not representable in source price units returns `422 bad_tick`; invalid scan bounds return `422 invalid_range`. GPU scans reject more than 16,000,000 candidate cells with `422 scan_limit`; narrow the period or price band, or increase the tick. They run on the heatmap-data service's bounded worker pool. Missing picture/CPU capacity returns 503.

The standard envelope contains `basis:"recording-twap-sum"`, `bandTick`, `loadedRange:[startMs,endMs]`, `recordedColumns`, `missingColumns`, a note, and `walls`. GPU results additionally contain `renderer:"gpu"`, `tick`, `range:{from_ms,to_ms,priceMin,priceMax}` and `unknownRows`. `loadedRange` in GPU mode is the advertised recording availability; it does not imply that those chunks are cached. `range` is the requested scan range. Unheld buckets count toward `missingColumns`, and veiled cells set `unknownRows`. Coverage is `complete` only when all selected columns are present and selected rows are valid, `partial` when some are present, otherwise `unknown`.

Each wall groups one price cell and side across time. Fields are `bucketStartMs` (the earliest peak), `priceLow`, `priceHigh`, `side:"bid"|"ask"`, `qty` (peak dominant-side resting quantity), `notional` (peak quantity times cell midpoint), `meanQty`, `firstSeenMs`, `lastSeenMs`, `columns` and `forming`. GPU rows also carry one-based `rank`; `forming` is true when the peak belongs to the current live bucket. Ranking is descending peak quantity, then ascending peak bucket, price low and side (bid first). Quantities in GPU mode are doubles from the CPU cell oracle, before display-code quantization. `meanQty` divides the sum of qualifying quantities by all recorded columns in the period, matching legacy semantics; `columns` counts qualifying appearances. Zero/invalid cells and quantities below `minQty` are excluded. These values describe aggregated resting size, not individual orders or proof of uninterrupted persistence.

The legacy renderer's recording projection is unchanged: omitted time bounds use the loaded window, explicit bounds intersect that window, the recorded-column budget remains 16M cells, `tick` does not change its band, quantities use the column's linear quantity code and scale, and `forming` stays false. An empty/unplaced projection returns empty unknown coverage. The non-recording legacy source returns `409 recording_required`: its separately normalized side channel and lack of a validity mask cannot supply reliable walls. Legacy scans remain on `DataProcessor`'s worker. In both renderer modes, a selection-epoch change during the scan returns `409 selection_changed`.

Book prices are dense-book bucket starts on `orderbook.tickSize` (see `/state`), not individual exchange price levels; sizes are the bucket totals rounded to 1e-8. Best bid and best ask are bucket prices too, so they can share a bucket and `spread` can read 0 when the real spread is under one tick.

Control (`POST`) and `GET /api/v1/operations/<id>` responses use the standard envelope: read `operationId`, `status`, `viewportVersion` and `frameId` under `data`. The screenshot response keeps its legacy flat shape.

Walls are price levels, not minutes: each (price cell, side) appears once with `qty` = its peak aggregated resting size in the range (`bucketStartMs` = when it peaked), `meanQty` = mean over recorded columns in the range (absent = 0), `firstSeenMs`/`lastSeenMs`, and `columns` = recorded minutes it was present. Use `priceMin`/`priceMax` to look away from the mid, where coarse cells otherwise sum the dense book near the price. The scan budget counts recorded columns only.
